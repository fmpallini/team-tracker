# src/core

Headless logic, no DOM construction. Loaded when working under `src/core/`.

- `types.ts` / `document.ts` — `Doc` shape, `SCHEMA_VERSION`, `migrate()` ladder (`MIGRATIONS[n]` mutates version-n doc to n+1; opening newer-schema file throws `SchemaTooNewError`). Bump schema + add migration whenever persisted shape changes (schema 16 renamed the template placeholders to English: `{date}` `{time}` `{person}` `{team}`; documented in `prefs_templates_placeholders_hint` and `help_templates_text` — keep them in step with `resolveTemplate`). `crypto.ts`'s `decryptDocumentWithVersion`/`parsePlainWithVersion` also return a file's pre-migration `schemaVersion` and its write `stamp` (see "Browser live store") from the same single decrypt/parse. Schema 18 added `Doc.docId` (random, immutable, keys the browser copy) and dropped the backup prefs; `autoSaveMin` is the file-write interval, 60–1440 minutes.
- `crypto.ts` — `.tmv` binary format (v2 container layout and images: see "Embedded images" below): `"TMV1"` magic + format version + PBKDF2-SHA256 (600k iterations) → AES-GCM, with key-check block so wrong password (`WrongPasswordError`) distinguishable from corruption (`CorruptFileError`). Payload `JSON.stringify(doc)`, run through `migrate()` on decrypt. Alongside encrypted path, `serializePlain`/`parsePlain` handle password-less files: ASCII `TMV-PLAIN\n` header line followed by raw `JSON.stringify(doc)` — fully human-readable, detected by sniffing that header before ever prompting for password.
- **Embedded images** (schema 17, container v2). `Doc.images` is metadata only (`{mime,w,h,bytes}` per id); the bytes live in `Store.images` (`image-store.ts`, never JSON-serialized). Ids are the first 32 hex chars of SHA-256 of the stored bytes (content-addressed, so the same picture is stored once); the note reference is a line `![alt](img:<id>)` (`image-ref.ts`). v2 layout: the v1 header (`bytes[4]=2`), `u32be docCipherLen`, the AES-GCM ciphertext of the JSON envelope `{doc, index}`, then the blob area (`blob-area.ts`) of individually sealed images (12-byte IV ‖ ciphertext, AAD = utf8 image id, so a blob cannot be swapped for another id). Plain: `TMV-PLAIN2\n` + one-line envelope + `\n` + raw blobs. v1 (`TMV1` version 1, `TMV-PLAIN\n`) stays readable and is lifted by `migrate()` (16→17, `images = {}`); files written now are always v2, which releases before 3.2.0 refuse. `blobCodec(password)` captures the session key, so the blob seal key must equal the header key: `change-password.ts` calls `images.rekey(newCodec)` before writing and rolls back to a fresh codec on failure.
  - **Sweep at serialization** (`doc-bytes.ts`): only images referenced from a markdown field (`collectImageRefs`) are written; unreferenced bytes stay in memory for the session, so delete → save → undo → save restores the picture. A missing or damaged blob never blocks open or save (placeholder, not adopted).
  - `image-import.ts` is the pure pipeline (magic-byte sniff, dedupe, 1 MB per image, 150 MB budget on referenced bytes, warn at 100 MB, animated GIF/APNG/WebP kept as original bytes if ≤ 1 MB); `ui/image-codec.ts` supplies the real decode/encode (WebP quality ladder, then 0.75× scale steps down to an 800 px long edge). Limits live in `IMAGE_LIMITS`; the README FAQ and the editor help text quote them, so change all three together.
- `store.ts` — single mutable `Doc` holder. Two mutation channels: `update(fn, scope?)` (marks dirty, notifies `subscribe()` — full content re-render) and `updateNav()` (nav-only, bypasses `subscribe()`). `onMutate()` fires on all three (`replaceDoc` as 'content'), receives `MutationKind`; `setReadOnly()` gates `update()` only. All prefs/content edits must go through `store.update`. `rev` monotonic mutation counter for cache invalidation — `Doc` mutated in place, so object identity never signals staleness.
- `scope.ts` — `ChangeScope`/`Section` plus pure `scopeAffects()` predicate letting `store.update()` describe what it changed. Absent scope means "everything changed" — unscoped call sites keep pre-scoping behavior. Never narrow scope not certain of: too narrow shows stale UI, too wide only costs redundant render.
- `switcher.ts` / `module-items.ts` — pure model of the Ctrl+Shift+K fast switch (Favorites → Due dates → Current team → Other teams; matching, favorite dedupe, 20-row cap via `allocateRows`) and the shared `buildModuleItems`/`titleFor` row builders. `ui/palette.ts` only renders it.
- `search.ts` — full-text search + backlinks, one `createSearchIndex` per document (owned by `ui/panes.ts`, fed by `store.subscribe` → `invalidate(scope)` and `store.onMutate` nav → `acknowledgeNav()`). Invalidation marks teams *stale*, never discards them: the next read re-collects the team's fields and reuses the prepared (`stripMd`+`normalize`d) form of every field whose `raw`/`title` is unchanged, so an edit costs its changed fields. The scope still decides *whether* a team is re-read — a scope that under-describes a change serves stale results — the text comparison only makes over-invalidating cheap. Ties rank by document order (`ScoredHit.order`), so narrowed and fresh results agree. `test/search-differential.test.ts` fuzzes the index against uncached `searchDocument`; extend its op list when adding a searchable field.
- `pane-layout.ts` — transient (never-persisted) half of pane layout: un-split stash and history stepping, extracted from `ui/panes.ts` so navigation policy sits apart from DOM rendering.
- `fs.ts` — File System Access API wrapper (`FileSession`), with download-fallback path for browsers without API (`session.handle === null` — no auto-save in that mode). Detects external file modification via `lastModified`, throws `ExternalChangeError` — but only when the bytes differ from what the session last read/wrote (`lastKnownBytes`), so a sync client or antivirus merely touching the file isn't a conflict. The `lastHandle` IndexedDB pointer is best-effort (`rememberHandle`): its failure must never fail a read/write that already succeeded.
- **Browser live store** (schema 18). IndexedDB is the live store of an open document; the `.tmv` file is a snapshot of it, written at open (when the browser copy is ahead), Lock/Close and on a 1–24 h timer. There is no manual save, no Ctrl+S, no blur/tab-hidden save, no backup file. The `Doc` and `store.update(fn, scope)` are untouched; everything below sits beside them.
  - `doc-records.ts` — `Doc` ⇄ path-addressed records: `doc` (minus teams/templates/images, plus `_order`), `team/<t>` (minus its collections, notes and daily notes, plus `_order`), `team/<t>/daily/<date>`, `team/<t>/general`, `team/<t>/<collection>/<id>`, `tpl/<id>`, `img/<id>`. Segments are `encodeURIComponent`-ed; `_order` lists record keys (a duplicate id in a damaged file gets a `~n` suffix, so it keeps its own record). Anything else on a doc/team rides in the remainder record, so a new scalar field is persisted without touching this file. Entity/template/image records alias the live objects — serialize before keeping them across an edit.
  - `live-db.ts` — raw layer, database `team-tracker-live` (separate from `idb.ts`): stores `meta`, `records`, `blobs`; one transaction per `commit` (atomic; `clear` replaces a whole document in the same transaction); `sharedLiveDb()` is the app's lazy connection (null when IndexedDB is unavailable). `LiveMeta` holds `lastWriteId`, `knownWriteIds` (last 20), `unwrittenChanges`, salt + check block.
  - `live-store.ts` — one document's slice. Rows are `{ s: sealed JSON of {path, value} }` (encrypted) or `{ v }` (plain) under random 128-bit hex keys, so no key reveals a title or date; AAD is `<docId>:<key>` (plus `crypto.ts`'s `live:` prefix), so rows cannot be swapped. Image blobs are stored exactly as the file holds them (`ImageStore.getStored`). A document that already has rows must be `load()`ed before the first `write` (unless `clear`). `rekey` re-seals everything in one commit and swaps the codec only afterwards.
  - `crypto.ts` additions: `recordCodec(password, salt?)` and `blobCodec(password, salt?)`. With no salt they use the session key (the open file's header key); with a foreign salt they derive on the side and never touch the session-key cache. The codec given to `createLiveStore` must come from the same call whose `salt` goes into `meta`, never a second lookup of the cache (the 3.2.0 header-key bug class).
  - `live-persist.ts` — watches `store.onMutate`, re-splits the doc on every flush (leading-edge 400 ms debounce) and commits only records whose JSON string differs from a cache of strings (never objects). Scope is deliberately not trusted. `unwrittenChanges` is sticky: a flush only raises it; `markFileWritten(stamp, revAtSnapshot)` / `adoptFileStamp(stamp)` lower it. A failed commit leaves the cache untouched and retries (`onErrorChange`). Its initial sync is *owed* until the store is writable (`Store.onReadOnlyChange`): only the tab holding the write lock may touch the browser copy, so `ui/open-document.ts` creates the store provisionally read-only wherever Web Locks exist. `reseed` (tab takeover) and `rekey` (password change) are ordered in the same chain as the flushes.
  - `live-open.ts` — reconcile at open, by identity and lineage, never by timestamp: `docId` keys the copy, a fresh `writeId` (in the envelope's `stamp`, `file-stamp.ts`) is set on every file write. no copy → import; same write, nothing unwritten → identical; same write + unwritten → browser newer (load it, rewrite the file, store starts dirty); write known but not latest → ask (older file); unknown write → file wins, or ask if the copy has unwritten edits. A copy under another password prompts for it (or falls back to the file); a plain copy is never used for a protected file; a newer-schema copy is never read; an unreadable one counts as absent. The file-wins replacement is one atomic commit.
  - `snapshot.ts` (`buildSnapshot` = bytes + fresh stamp + rev before serializing; `commitSnapshot` never throws), `file-snapshot.ts` (the three write moments + explicit export; `FileHealth`; single-flight; `runExclusive` for the password change; `isOverdue` for the window-close prompt; the timer re-arms a full interval after a failed attempt), `close-document.ts` (Lock/Close: editors → browser copy → file → teardown; a failed write opens the write-failed dialog; a conflict result never stacks a dialog) and `createBeforeUnloadHandler`. UI companions: `ui/write-failed.ts`, `ui/reconcile-dialogs.ts`, `ui/file-health-toasts.ts`, `ui/open-document.ts`.
- `change-password.ts` — re-encrypts (or plain-serializes, for password ↔ password-less transition) the current doc under the new password inside `file-snapshot.ts`'s `runExclusive()`: flush the browser copy, re-key the image store, write the file (a failure rolls back only the image codec), commit the stamp, then `persister.rekey` the browser copy under the same key (a failure there keeps the file write and the old, consistent key; the next open asks for the old password). Extracted out of `main.ts` specifically so this concurrency-sensitive path is unit testable.
- `tab-lock.ts` — cross-tab single-writer coordination (Web Locks API + `BroadcastChannel` "take control" handshake). A hand-over flushes the holder's editors and browser copy (`flushLive`) — no file write; if that fails the holder keeps the lock and the asker re-clicks. The tab that takes over reloads from the browser copy (`main.ts`'s `reloadFromLive`, with `persister.reseed`), not from the file. Repeated "Take control" clicks queue one lock request only. Extracted out of `main.ts`, with `navigator.locks`/`BroadcastChannel` passed in as deps so tests can fake them (jsdom has no Web Locks API at all).
- `reload-document.ts` — decodes the bytes now on disk for the conflict-modal Reload: tries plain first, then the current password, then asks (`askPassword`), because another tab may have changed or removed the password. Extracted from `main.ts` so it is unit-testable.
- `idb.ts` — minimal single-connection IndexedDB key/value wrapper (`idbGet`/`idbSet`/`idbDel`), persists the file handle and the auto-open-last flag across sessions (the live store has its own database, `live-db.ts`). Every *other* module mocks this out; own tests use `fake-indexeddb` (dev-only) since jsdom has no real `indexedDB`.
